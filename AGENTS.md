# NixOS Config

> **Keep this file current.** Update the relevant section when changing aspects, hosts, Den patterns, or flake layout.

## Safety

- NEVER run `nixos-rebuild switch` or `nixos-rebuild boot`
- Safe eval commands: `nix flake check` or a targeted, bounded system-derivation evaluation. Do not evaluate full host attrsets or run host evaluations in parallel; the recursive module values can overflow or consume excessive resources. For example:
  ```sh
  timeout --signal=TERM --kill-after=5s 45s nice -n 10 nix eval --raw .#nixosConfigurations.WeebMachine.config.system.build.toplevel.drvPath
  timeout --signal=TERM --kill-after=5s 45s nice -n 10 nix eval --raw .#darwinConfigurations.Astraeus.config.system.build.toplevel.drvPath
  ```
- Never touch: `secrets/` `assets/`
- Never delete a file without asking first
- Run `git add -A && git commit` before making large changes
- Never push unless the user explicitly requests it for the current task. Prior push requests do not authorize future pushes, and requests for a clean or committed working tree do not imply permission to push.

## Flake Management

`flake.nix` is generated by [flake-file](https://github.com/vic/flake-file).
`inputs.import-tree ./modules` recursively discovers all `.nix` files, including profiles.

- **Add/change a flake input:** edit `modules/inputs.nix` (or the relevant aspect file using `flake-file.inputs`)
- **Regenerate flake.nix:** `nix run .#write-flake`

## Den API — Non-Negotiable Rules

- Never use deprecated `den.ctx`; use `den.aspects`, `den.schema`, `den.default`, and `den.policies`.
- Home-manager wiring is **automatic** when users have `classes = ["homeManager"]` and `home-manager` is in the flake inputs.
- Do NOT set `home-manager.useGlobalPkgs` or `useUserPackages` manually.
- Do NOT manually import `inputs.home-manager.nixosModules.home-manager`.
- `inputs` is a module argument everywhere — no `specialArgs` needed.
- Flat-form class modules **must** include `...` in args or eval will crash:
  ```nix
  nixos = { host, config, pkgs, ... }: { ... }   # correct
  ```

## Aspect File Structure

Every aspect uses the attrset form (not dot-chained assignments):

```nix
{ den, inputs, ... }:
{
  den.aspects.foo = {
    nixos = { host, config, pkgs, lib, ... }: { ... };
    darwin = { host, config, pkgs, ... }: { ... };
    homeManager = { host, config, pkgs, ... }: { ... };
    includes = [ den.aspects.bar ];
  };
}
```

- Omit unused blocks; keep class blocks ordered `nixos`, `darwin`, then `homeManager`.
- Keep set-like `includes`, package, app, and cask lists alphabetized when their order is not semantic. Keep baseline profiles before host-specific overrides, and preserve intentional precedence or grouping elsewhere.
- OS class blocks apply only to their platform. Guard Linux-only Home Manager
  settings with `pkgs.stdenv.hostPlatform.isLinux` and Darwin-only settings with
  `pkgs.stdenv.hostPlatform.isDarwin`; shared aspects must evaluate safely when
  included by either NixOS or Darwin hosts. Use `host.class` only in schema or
  policy contexts, or in import lists that must be resolved before `pkgs` is
  available.

## Batteries — All Opt-In

| Battery | What it does | Where to include |
|---|---|---|
| `den.batteries.define-user` | sets the host user's OS account and Home Manager home path | `setup.nix` → `den.default.includes` |
| `den.batteries.hostname` | sets `networking.hostName` from `host.hostName` | `setup.nix` → `den.default.includes` |
| `den.batteries.primary-user` | NixOS wheel + networkmanager groups; Darwin `system.primaryUser` | `aspects/user.nix` → user aspect `includes` |
| `den.batteries.user-shell "fish"` | fish shell at OS + HM level | `aspects/user.nix` → `den.aspects.weeb` and `den.aspects.nolan` |
| `den.batteries.host-aspects` | wires host-named aspect to its host | `aspects/user.nix` → `primaryUser` |

Do NOT manually declare a host user's `users.users.<name>` account, `home.username`, `home.homeDirectory`, or a battery-owned shell — batteries own these.
`den.aspects.primaryUser` is the shared aspect for `primary-user` and `host-aspects`; both `weeb` and `nolan` consume it and the Fish user-shell battery.

## Profiles (`modules/aspects/profiles/`)

- `base`: portable Home Manager tools, terminals, Git, file management, and monitors; excludes storage, desktop services, Darwin casks, and personal apps.
- `nixosBase`: NixOS cache, locale, and optimization policy.
- `nixosStorage`: Disko/Btrfs/impermanence and rollback for the existing NVMe/LUKS/Btrfs layout; not a generic server profile.
- `nixosSecurity`: persistence-backed identity/security; requires compatible storage for its `environment.persistence` declarations.
- `linuxDesktop`: Linux Home Manager desktop settings plus NixOS services/packages. Rofi belongs here rather than `base`.
- `workstation`: `base` plus personal apps, development, gaming, AI, browser, communication, VPN, and editors; opt-in for servers.

Select profiles explicitly; `base` alone is not a complete host. Linux Home Manager
guards also apply outside NixOS: standalone users can select `linuxDesktop`'s Home
Manager settings while the external OS supplies services and the compositor.

Storage contracts:

- The initrd embeds `scripts/rollback-btrfs.sh`. Recovery subvolumes use `archived-<epoch>-<counter>` names and retain 30 days after archival; recognized legacy mtime names get a fresh 30-day migration grace period. Unknown names, ordinary directories, and symlinks are excluded from cleanup.
- `impermanence` runs `scripts/persistent-storage-report.py` monthly as the host user, read-only against `/persistent`. Sizes cover readable metadata only; it compares declarations with live bindings, flags incomplete scans, excludes protected directories/symlinks, and never treats missing mounts as orphan declarations or deletes data.
- Report JSON history/text persist in `/var/lib/persistent-storage-report` (`0700`, files `0600`). Linux Home Manager shows each summary once in Fish using persisted universal variables.

## Feature Ownership and Exceptions

- Fish configuration is Home Manager-owned; Linux persistence is NixOS-only. The Den battery owns Darwin `/etc/shells`; activation reconciles the existing admin user's login shell. Do not duplicate battery settings.
- Git is Home Manager-owned, including platform-derived `safe.directory`; Linux `.config/gh` persists with mode `0700`. Shared keyring persistence belongs to `security.general`.
- `dev` supplies portable Home Manager tools and NixOS integration; activation creates mutable `~/projects` idempotently.
- `workstation.homeManager` owns personal apps/CLI packages; Linux system packages belong to the relevant role profile. Filen uses `pkgs.unstable.filen-desktop` on both platforms.
- Ghostty uses Home Manager `ghostty` on Linux and `ghostty-bin` on Darwin. LocalSend is shared Home Manager; firewall/persistence are NixOS-only.
- Matugen themes, Qt/QML paths, desktop entries, and persistence remain Linux-guarded or NixOS-only. ONLYOFFICE and Celluloid have no declared Mac replacements. Apple Command Line Tools and cross-host synchronization remain deferred.

### Codex and browsers

- `den.aspects.ai.provides.chatgpt` owns `programs.codex`, `pkgs.llm-agents.codex`, plugins, skills, MCP, and oh-my-codex on both platforms; retain upstream Codex input/program names. Its Darwin block declares only the official `chatgpt` Homebrew cask.
- NixOS persists `.codex`, `.config/Codex`, `.config/codex-desktop` (`0700`, including pairing keys), and `.local/state/codex-desktop`. Do not separately persist the pairing-key child directory; caches stay ephemeral, keyring persistence stays in `security.general`.
- Linux Home Manager supplies `codex-desktop-linux`, Computer Use UI, mobile control, and one declarative remote-control service; community anonymous usage reporting is disabled in both session environments.
- Desktop's private `cliPackage` adapter (`scripts/codex-desktop-proxy.py`) translates only `app-server proxy` from JSONL to the service's Unix WebSocket transport. Other commands, the CLI, and the remote-control service use the regular package. Retire the adapter when upstream Desktop supports this transport.
- Home Manager owns browsers, including shared `pkgs.unstable.brave`. Linux extensions use `programs.chromium`; Darwin uses root-owned Brave/Chrome managed-preferences plists, never Home Manager files inside browser profiles.
- Shared `bravePolicies` feeds Linux `programs.chromium.extraOpts` and Darwin `/Library/Managed Preferences/com.brave.Browser.plist`. Both Darwin reconcilers run on activation and native path events; a configuration-profile fallback remains deferred.

### Homebrew, gaming, and VPN

- `nix-homebrew` bootstraps native ARM `/opt/homebrew`; nix-darwin reconciles declared packages with cleanup `uninstall`, mutable taps, and native updaters enabled. `homebrew` supplies infrastructure; feature aspects declare casks through module merging, outside Nix app links and MAS.
- `gaming` is included once through `workstation`. Shared Home Manager owns `pkgs.prismlauncher` and Java runtimes; do not add a Prism cask. Linux Heroic uses NixOS `pkgs.warm.heroic`; Steam, ProtonPlus, compatibility tools, persistence, and `ntsync` stay NixOS-only.
- `gaming.darwin` owns `crossover`, `heroic`, `notprotonnot/notproton/notproton`, and `steam` casks; do not duplicate CrossOver/Heroic through Nix. NotProton uses the upstream `notprotonnot/notproton` tap without a post-install script; approval/runtime setup is manual. Steam requires Rosetta; CrossOver activation remains private user state.
- `gaming.darwin` also declares Wuthering Waves (`6475033368`) through `programs.mas.packages`; the host owns MAS enablement and cleanup policy.
- `proton` owns Linux `pkgs.proton-vpn` and Darwin `protonvpn`. WeebMachine persists `.config/Proton`; caches/logs are ephemeral, keyring/NetworkManager persistence stays in security aspects. Valve Proton belongs to `gaming`; Proton Pass is not declared.

### Linux system policy

- `optimizations.nixos`: one Zstd Zram device capped at 8 GiB or half of RAM; no disk swap, writeback, hibernation, or swappiness override.
- `printing` persists `/var/lib/cups`. With AppArmor, it adapts Avahi's packaged policy to Nix-store paths, selects it on the service, waits for the policy loader, and restarts on policy changes while retaining upstream sandboxing.
- `security.general` enforces `nixos-ping` on the Nix-store iputils executable behind the capability wrapper. Packaged profiles are parser includes, not loaded policies; broader confinement needs compatibility and denial tests.
- `security.systemd`: coredumps limited to 1 GiB total, per dump, and processing; seven-day mtime retention. Preserve other upstream tmpfiles rules; unexpected upstream coredump-rule changes must fail the build for review.

## Adding a New Aspect

1. Create `modules/aspects/<name>.nix` with the attrset form above. Use `homeManager` for portable user configuration, `nixos` for Linux system integration, and `darwin` for macOS system integration.
2. Add `den.aspects.<name>` to the narrowest appropriate profile file in `modules/aspects/profiles/`, or directly to a host file if it is host-only. Keep `base` limited to genuinely portable Home Manager baseline features.
3. If it needs a new flake input, declare it via `flake-file.inputs` inside the aspect file, then run `nix run .#write-flake`.
4. Update this AGENTS.md if the aspect introduces a new pattern or has host-conditional behavior.

## Adding a New Host

1. Create `modules/aspects/hosts/<hostname>/` with `<hostname>.nix`; add `hardware.nix` for NixOS hosts when needed.
2. Declare `den.hosts.<system>.<Hostname>` with the host's `users.<name> = {}`.
3. Declare `den.aspects.<Hostname>` with explicit role profiles such as `nixosBase`, `nixosStorage`, `nixosSecurity`, `linuxDesktop`, or `workstation`, then add only host-specific or platform-specific aspects and overrides. Do not assume `base` is a complete host configuration.
4. Update this AGENTS.md with the new host's summary.
