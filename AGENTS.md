# NixOS Config — Working Rules

Keep these rules current when changing architecture or maintenance contracts.
Configuration details belong in their owning modules; deferred work belongs in
`TODO.md` and Mac setup instructions in `docs/astraeus-manual-setup.md`.

## Safety and scope

- NEVER run `nixos-rebuild switch` or `nixos-rebuild boot`. Do not activate,
  reboot, change services, or modify boot state without explicit task authorization.
- Never touch `secrets/` or `assets/`; never decrypt or print sensitive values.
- Never delete a file without asking first. Preserve existing work and record
  Git status before substantial edits.
- Stage only reviewed paths/hunks. Commit only with explicit approval for the
  current task; push only when explicitly requested for that task.
- Public prose describes technical configuration and maintenance. Exclude
  conversational approvals, personal timelines/decision dates, handoffs, internal
  task IDs, execution narratives and private-project reports. Review the exact
  staged diff and metadata for privacy before approved publication.

## Validation

Never evaluate full host attribute sets or hosts in parallel. Use bounded,
sequential system-derivation evaluations with lock updates disabled:

```sh
timeout --signal=TERM --kill-after=5s 45s nice -n 10 nix eval --no-update-lock-file --raw .#nixosConfigurations.WeebMachine.config.system.build.toplevel.drvPath
timeout --signal=TERM --kill-after=5s 45s nice -n 10 nix eval --no-update-lock-file --raw .#darwinConfigurations.Astraeus.config.system.build.toplevel.drvPath
```

`nix flake check --no-update-lock-file` and non-activating builds are allowed.
Use an explicit `path:/home/weeb/nixos` source when required new files are not
indexed by Git. If staging is authorized, add only reviewed intended files.
Do not update inputs or regenerate the flake unless the task calls for it.

## Structure and Den

- `flake.nix` is generated by flake-file: edit `modules/inputs.nix` or an owning
  aspect's `flake-file.inputs`, then use `nix run .#write-flake`. Never edit the
  generated flake manually.
- `inputs.import-tree ./modules` discovers `.nix` modules except paths containing
  `/_`. Import underscore helpers explicitly; do not change discovery rules.
- Keep feature code in `modules/aspects/`, role bundles in `profiles/`, host
  selection in `hosts/`, schema in `modules/schema.nix`, and shared setup/overlays
  in `modules/setup.nix`. `base` alone is not a complete host.
- Keep an app's package, persistence and optional policy in its app aspect file;
  put long optional policy definitions below ordinary configuration.
- Use `den.aspects`, `den.schema`, `den.default` and `den.policies`, never
  deprecated `den.ctx`. `inputs` is already a module argument; no `specialArgs`.
- Use attrset-form aspects and omit unused blocks. Flat class-module argument sets
  must include `...`.
  Keep class blocks ordered `nixos`, `darwin`, then `homeManager`:

```nix
{ den, inputs, ... }:
{
  den.aspects.example = {
    nixos = { host, config, pkgs, lib, ... }: { };
    homeManager = { pkgs, ... }: { };
    includes = [ den.aspects.other ];
  };
}
```

- Home Manager wiring is automatic with `classes = [ "homeManager" ]`; do not
  manually import its NixOS module or set `useGlobalPkgs`/`useUserPackages`.
- Den batteries own host users, home paths, hostnames and user shells. Do not
  duplicate their account, `home.username`, `home.homeDirectory` or shell settings.
- Alphabetize set-like includes/package/app lists unless order is semantic.
  Preserve baseline-before-override precedence and shared overlay order.
- Guard platform-specific Home Manager settings with
  `pkgs.stdenv.hostPlatform.isLinux`/`isDarwin`. Reserve `host.class` for early
  schema/policy/import decisions. Keep Linux services and persistence NixOS-only.
- Use schema-provided host values. The supported desktop checkout is `~/nixos`;
  do not silently promise alternate-path support. Do not bump state versions
  merely because package inputs change.

## Preserve maintenance boundaries

- Optional app confinement toggles default to disabled; enable them only when
  separately approved. Requalify policy/package/kernel changes; direct-file confinement is
  not complete IPC, credential or network isolation. Do not weaken native sandboxes.
- Rollback must preserve complete readonly checkpoints and per-node identities,
  allocate both restore trees before moving roots, and retain distinct observed
  versions. Never consume unresolved checkpoints or re-expose sole parked data.
  Completed retirement must never restore live roots. Do not add a success-required
  boot gate or expand pruning to protected/unknown names. Qualify storage changes
  in disposable Btrfs guests, including old-script fallback and space pressure.
- Persistence reporting is read-only. Incomplete scans, missing mounts and old
  timestamps do not authorize deletion; retain private history permissions.
- Preserve guarded upstream-drift assertions and compatibility overrides until
  equivalent upstream behavior is verified. Do not bypass guards to make a build pass.
- Preserve Blender/Codex's single pinned registration, loopback/safety/privacy
  controls, stable launcher and mutable-cache ownership. Keep its preservation
  guard before both `cleanCodexPluginCache` and `writeBoundary`; never overwrite
  cache collisions or saved preferences. Use the existing disposable smoke test.
- Do not rewrite private app databases, browser profiles or permissions to bypass
  macOS approvals. Keep `linkApps` collision protection; `copyApps` requires a
  separate TCC/App Management decision. Licenses, downloads and sign-ins remain
  explicit setup steps, not activation side effects.
- Preserve project trust entries, app/agent permissions, font/link declarations,
  dormant-feature opt-ins and hardware/retention policy unless requested.
  Keep the installer unpinned and its SSH override fail-on-drift; installation
  still requires target inspection and erase confirmation.
